# 개발 결과 검토 규약

## 역할과 검토 범위

개발 에이전트는 구현·자체 테스트·증거를 책임진다. 검토 에이전트는 보고서, 실제 코드, 스펙, 테스트 결과, 가능한 실행을 교차 확인한다. 사용자가 별도 요청하지 않는 한 검토자는 제품 코드를 동시에 수정하지 않고 검토 문서와 수정 요청을 남긴다.

검토 시작 시 대상 commit 또는 파일 상태를 고정한다. 개발 에이전트는 검토 중 같은 파일을 바꾸지 않는다. 추가 수정이 생기면 이전 검토가 어느 상태에 대한 것인지 기록하고 영향 범위만 다시 검토한다.

## 개발 보고 양식

`docs/reviews/Mx-developer-report.md`에 아래 형식을 사용한다. 문서가 아직 없으면 개발 에이전트가 작성한다.

```markdown
# Mx 개발 완료 보고

- 작성 일시:
- 프로젝트 경로:
- 대상 commit SHA 또는 Git 미사용 사유:
- 미커밋 변경 여부와 목록:
- 완료 태스크 / 미완료 태스크:
- live / mock / replay 구분:

## 구현과 요구사항

| REQ/T ID | 실제 구현 파일·심볼 | 동작 | 검증 근거 |
|---|---|---|---|

## 재현 방법

- 환경·의존성 버전:
- 설치/실행 명령과 실행 디렉터리:
- 필요한 환경변수 이름(값 제외):
- 초기 데이터 생성과 테스트 DB 격리 방법:
- UI 주소·동작 확인 순서:

## 실제 수행한 검증

| 명령 | 결과·종료 코드 | 시각 | 로그/보고서 경로 |
|---|---|---|---|

## 실제 NVIDIA 사용 증거

- 모델 ID·설정 hash·run ID:
- NAT 실행/평가/프로파일 산출물:
- Skill API 요구 확인 상태·출처:
- OpenShell 사용/미사용/미검증 및 근거:

## 실패·한계·남은 작업

- 알려진 결함과 재현 방법:
- 환경 제약 때문에 못 한 검증:
- 사용자 결정/계정 작업이 필요한 항목:
- 스펙 변경 내용과 이유:
```

실행하지 않은 명령을 테스트 결과에 넣지 않는다. “테스트 통과” 대신 어떤 범위를 몇 건 확인했는지 기록한다. 비밀값이나 환경변수 전체 dump를 첨부하지 않는다.

## 검토자가 직접 확인할 항목

| 영역 | 확인 방법 |
|---|---|
| 스펙 일치 | 완료 체크된 T/REQ를 실제 구현과 연결, 빠진 기능 표시 |
| 업무 안전 | 동시·반복 환불, 승인 우회, 소유권, 견적 만료·변경 테스트 |
| 변경 후 실패 | commit 후 timeout에서 재환불이 발생하지 않는지 확인 |
| 자동 생성의 실체 | candidate source trace, 전체 순서, 새 ID 바인딩, 하드코딩 여부 |
| 승격과 정책 | validation 분리, 불합격 후보 활성화 불가, stale 버전 차단 |
| 모델 연결 | 실제 호출 증거, mock fallback 숨김 여부, 루프 상한·오류 표시 |
| NVIDIA 활용 | 실제 의존성과 호출 경로 확인, 명칭만 적은 통합 구분 |
| 평가 | A/B/C 조건·분모·누락·실패, test 누출, report 재집계 |
| UI | 정상/빈 상태/오류/승인/재생/미측정 표시, 핵심 E2E |
| 재현성 | lockfile, 환경변수 안내, 깨끗한 테스트 데이터, README 절차 |
| 제출물 | 주장과 코드·영상·보고서 일치, PDF 열림·링크 접근 |

실제 API/브라우저/격리 환경 접근이 없어 검증하지 못한 항목은 “확인 불가”로 남긴다. 정적 코드 검토로 runtime 성공을 대신 판정하지 않는다. 테스트는 실제 외부 결제·데이터 변경이 없는 모의 환경에서 수행한다.

## 검토 결과 양식

`docs/reviews/Mx-review.md`:

```markdown
# Mx 검토 결과

- 검토 대상 commit/파일 상태:
- 검토 일시:
- 판정: 다음 단계 진행 가능 / 수정 후 재검토 / 증거 부족
- 실제 수행한 검증:
- 수행하지 못한 검증:

## 발견 사항

| ID | 심각도 | 파일·위치 | 재현 조건 | 영향 | 수정 요구 | 확인 테스트 |
|---|---|---|---|---|---|---|

## 제출 주장에 반영할 내용

- 확인된 구현:
- 계획/미검증으로 남길 내용:
- 수치 또는 문구 수정:

## 개발 에이전트에게 전달할 다음 지시

수정할 ID, 범위, 완료 조건을 명시한다.
```

심각도: P0=잘못된 환불·권한 우회·비밀 노출 등 즉시 차단 필요, P1=핵심 흐름/검증/제출 근거의 중대 실패, P2=제한적 오류·UX 문제, P3=선택 개선. 미해결 P0/P1은 최종 제출 준비 완료 판정을 막는다. 단계별로 미래 태스크의 미구현은 결함과 구분한다.

## 운영 방법

개발 보고 → 검토 요청 → 직접 확인 → 수정 지시 → 개발 에이전트 수정·재검증 → 다음 단계 순서로 진행한다. 단계마다 사용자에게 기술 선택을 다시 묻는 절차는 만들지 않는다. 계정 정보·팀명·실제 동의처럼 당사자가 결정해야 하는 항목만 별도로 남긴다.
