# TraceMakers / SkillForge 심사 대비

## 20초 소개

저희 TraceMakers의 SkillForge는 에이전트 실행 경험을 검증된 업무 절차로 전환하고, 정책이 바뀌면 재사용 가능성을 다시 확인하는 운영 콘솔입니다. 승인 기준이 50만원에서 30만원으로 바뀔 때 35만원 환불의 판정이 어떻게 달라지는지 비교하고, 기존 절차를 중지한 뒤 새 버전을 검증·활성화하는 과정을 보여드립니다.

## 가장 중요한 질문과 답변

### 1. 그냥 환불 챗봇이나 RPA와 무엇이 다른가요?

핵심 사용자는 환불 고객보다 자동화 담당 운영자입니다. 실행 기록의 출처에서 절차를 구성하고, 독립 검증과 정책 변경 전후 결과를 같은 화면에서 확인할 수 있습니다. 수동 워크플로도 빠르게 실행할 수 있으므로 단순 속도 우위를 주장하지 않습니다. 어떤 근거로 자동화를 다시 사용해도 되는지 판단하는 흐름을 구현한 것이 차별점입니다.

보여줄 것: 정책 미리보기의 35만원 사례 → 이전/이후 판정 → 새 후보의 부모 hash.

### 2. 6단계를 이미 정해 놓았다면 AI가 꼭 필요한가요?

이 환불 절차 하나만 실행하는 데 AI가 필수는 아닙니다. MVP에서는 NVIDIA 모델이 실제 도구를 선택·호출한 기록을 수집하고, 그 기록을 재사용 가능한 절차와 검증 근거로 전환하는 과정을 입증했습니다. 지원하는 도구 순서는 사람이 제한한 6단계입니다. 임의 업무를 자동 발굴하는 범용 시스템이나 모델 학습으로 소개하지 않습니다. 확장 가치는 더 다양한 업무에서 별도로 검증해야 합니다.

보여줄 것: 실제 model.completed/tool.requested 이벤트와 source trace 5건. 설명할 것: 모델의 유연성과 실행기의 엄격한 권한 경계를 분리했다.

### 3. 자동 생성인가요, 템플릿 복사인가요?

현재 코드는 요청·완료 이벤트를 읽어 단계와 인자 참조를 구성합니다. 실제 quote 출력과 다음 입력의 값·타입·시간 순서를 대조하고 동일한 정규화 단계들을 그룹화합니다. 수동 템플릿 함수를 호출하지 않는 테스트도 있습니다. 다만 결과가 허용된 환불 6단계와 일치해야 하므로 제한된 도메인 컴파일러이며 범용 프로그램 합성은 아닙니다.

근거: backend/compiler.py, backend/engine.py, tests/test_policy_lab.py.

### 4. 승인 기준을 바꾸면 무엇이 실제로 달라지나요?

승인 기준이 50만원에서 30만원이 되면 35만원 환불이 자동 처리에서 운영자 승인 필요로 바뀝니다. 먼저 동일 사례를 구·신 정책의 격리 DB에서 비교합니다. 변경 적용 시 기존 절차를 STALE로 제외하고, 부모 출처를 가진 새 후보가 현재 정책에서 검증을 통과해야 다시 활성화할 수 있습니다. 임계값만 바꾼 가짜 버전 이벤트가 아니라 실제 판정 변화입니다.

### 5. 최신 정책을 실행 시 검사하면 재검증은 왜 필요한가요?

실행 시 검사는 필수이고 이미 모든 경로에 적용합니다. 재검증은 운영자가 변경 전에 정상 요청의 처리 방식·차단 여부를 확인하고, 승인한 버전과 보고서를 연결하기 위해 추가한 과정입니다. 현재 구현은 임계값 변경과 6단계 절차에 한정합니다. 재검증이 모든 미래 오류를 증명하거나 런타임 검사를 대체하지는 않습니다.

### 6. NVIDIA 기술을 실제로 어디에 사용했나요?

NVIDIA hosted Nemotron의 tool calling으로 합성 환불 업무를 실행하고 공개 도구 이벤트·사용량·DB 결과를 저장했습니다. NeMo Agent Toolkit은 자체 bounded agent를 실행하는 custom workflow 플러그인으로 통합했고, NAT CLI live 증거가 있습니다. MCP는 같은 gateway의 도구 6개를 stdio로 노출합니다. 웹 콘솔의 모든 요청이 NAT나 MCP를 반드시 통과한다고 주장하지는 않습니다.

근거: artifacts/policy-change-evidence.json, nat-live-evidence.json, mcp-evidence.json.

### 7. Skill API 요건과 NemoClaw/OpenShell도 충족했나요?

현재 실제 검증한 범위는 NVIDIA hosted Nemotron, NAT custom workflow, MCP 통합입니다. 신청서의 Skill API가 구체적으로 어떤 API와 증빙을 뜻하는지는 주최측에 문의했고 확인 답변을 기다리고 있습니다. NemoClaw/OpenShell OS 격리는 검증하지 않았습니다. 앱의 업무 정책 검사와 OS 격리를 같은 기능이라고 설명하지 않습니다.

금지 표현: “NVIDIA API를 썼으니 Skill API 요구는 무조건 충족”, “OpenShell 보안 검증 완료”.

### 8. 검증 수치가 여러 개인데 각각 무슨 뜻인가요?

회귀 57건은 코드의 동작·실패·권한 경계 검사입니다. 안전 행렬 36건은 12종 합성 사례를 3경로에서 실행한 별도 검사입니다. 후보 검증은 discovery에 쓰지 않은 30개 사례와 현재 정책 경계 6개입니다. 정책 비교 42쌍은 30개 validation과 구·신 기준의 경계 12개를 두 정책에서 실행한 것으로, 84회의 모델 호출이 아닙니다. 경계군에는 금액·상태가 반복되는 사례가 있습니다.

### 9. 0건의 위험 변경이면 안전하다는 뜻인가요?

해당 합성 실험에서 독립 DB oracle가 위험한 변경을 찾지 않았다는 뜻입니다. 산업 전체 안전성이나 모든 공격에 대한 증명이 아닙니다. 정상 요청의 과도한 차단도 별도로 측정합니다. 실제 결제 환경에서는 외부 결제 상태 조회, 정산 대조, 운영 인증과 감사 체계가 추가로 필요합니다.

### 10. 실제 모델이 실패한 적도 있나요?

네. 신규 정책 비교에서 변경 전 실행이 NVIDIA HTTP 500으로 실패했고 원본을 보존했습니다. 새 격리 주문의 별도 재실행은 성공했습니다. 변경 후 35만원 요청의 승인 대기도 실제 모델로 확인했습니다. 최초 실패를 숨기지 않아 policy-change-evidence.json의 종합 passed 값은 false이고, 별도 성공은 policy-change-live-retry.json에 있습니다.

### 11. 성능이나 비용이 얼마나 좋아졌나요?

이전 버전의 합성 pilot에서 같은 40개 사례에 대해 에이전트 모델 호출 244회, 수동·생성 절차는 각각 0회였습니다. 기대 판정 일치는 34/40, 40/40, 40/40입니다. 공급자 오류를 포함했고 자연어 라우터와 실제 결제 비용은 제외했습니다. 새 정책 기능의 성능 수치가 아니며, 수동 절차보다 빠르거나 실제 운영비를 특정 비율 절감했다고 주장하지 않습니다.

### 12. 정책 변경이나 승인 요청이 동시에 들어오면요?

SQLite 거래 안에서 최신 상태와 정책을 확인하고 승인 소비·환불을 함께 확정합니다. 미리보기 적용은 기본 정책 hash를 다시 비교하므로 오래된 미리보기가 새 정책을 덮어쓰지 못합니다. 이전 정책의 승인은 새 정책에 사용할 수 없습니다. 새 후보의 검증·활성화 시에도 정책이 바뀌지 않았는지 확인합니다. 이는 로컬 DB 범위의 보장이며 분산 결제의 exactly-once는 아닙니다.

### 13. 환불 후 응답이 끊기면 다시 환불하지 않나요?

쓰기 이후 결과가 불확실하면 NEEDS_RECONCILIATION과 보류 기록을 남겨 추가 쓰기를 막습니다. 운영자가 DB 상태를 확인한 뒤 처리하도록 합니다. 동일 주문의 중복 환불은 거래와 unique 제약으로 차단합니다. 실제 외부 결제 연동에서는 제공자 idempotency와 정산 대조가 추가로 필요합니다.

### 14. 데이터가 너무 단순하고 테스트에 맞춘 것 아닌가요?

맞습니다. 현재는 실제 고객 데이터가 아닌 합성 환불 데이터이며, discovery/validation/test의 ID·텍스트·seed를 분리했지만 반복되는 상태 유형이 많습니다. 분리 자체가 새로운 업무에 대한 일반화 증거는 아닙니다. 다음 단계는 익명화된 운영 사례, 다양한 정책 변경과 다회 반복 평가, 운영자 사용자 테스트입니다. 아직 수행한 것처럼 말하지 않습니다.

### 15. 사업성이나 고객 검증은 있나요?

초기 대상은 금전 변경 권한 때문에 AI 자동화 도입을 주저하는 커머스 운영·자동화 담당자입니다. 정책 변경 시 영향을 추적하고 승인 근거를 남기는 시간을 줄일 수 있다는 가설입니다. 고객 인터뷰·유료 도입·절감 시간은 아직 측정하지 않았습니다. 후속 실험은 수동 갱신과 SkillForge 갱신의 작업 시간, 놓친 영향 사례, 정상 오차단을 비교하는 것입니다.

### 16. 기존 agent memory 연구와 독창성은 무엇인가요?

경험에서 workflow를 재사용하는 연구와 durable workflow·사람 승인 기능은 이미 있습니다. 저희는 그것을 최초라고 주장하지 않습니다. 변경 업무의 실행 출처, 정책 전후 사례 비교, 독립 상태 판정, 새 버전의 명시적 활성화를 운영자가 이해하는 하나의 흐름으로 연결했습니다. 연구적 새로움보다 일관된 구현과 검증 가능한 적용 사례로 평가받고자 합니다.

참고: [Agent Workflow Memory](https://arxiv.org/abs/2409.07429). 코드와 실측의 한계는 docs/reviews/policy-change-release.md를 따른다.

## 시연 중 장애 대응

- Live 오류: 오류를 보여주고 run ID를 남긴다. 사전 수집 live 증거를 “저장된 실행 기록”이라고 밝히고 설명한다.
- API 제한: Mock으로 전환한다면 먼저 전환을 알린다. Mock 성공을 live 성공처럼 표시하지 않는다.
- 이미 환불한 주문: 정상 성공을 보이려면 새 주문을 생성한다. 기존 주문은 중복 차단 시연에 사용한다.
- 현재 승인 기준이 이미 30만원: 먼저 50만원으로 영향 비교·적용·재검증·활성화를 거쳐 초기 상태를 준비하거나, 반대 방향 변화임을 설명한다.
- 운영자 인증: 본인 로컬 세션으로 연결한다. NVIDIA 키를 세션 입력란에 넣거나 화면에 보여주지 않는다.

## 팀 리허설 방법

기능 담당자는 3분 시연, 다른 팀원은 1·2·5·7·10·14번 질문을 순서 없이 묻는다. 답변은 먼저 결론 한 문장, 근거 한 가지, 한계 한 문장으로 30~45초 안에 끝낸다. 담당 역할은 실제 기여에 따라 소개하고 존재하지 않는 고객 성과·팀원 역할을 만들지 않는다.

마지막 문장: “저희가 보여드린 것은 자동화가 한 번 성공하는 장면뿐 아니라, 정책이 바뀐 뒤에도 다시 사용할 근거를 확인하는 과정입니다.”
